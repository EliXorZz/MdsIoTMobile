# J2 — Fraîcheur, reprise et doublons

## Questions à répondre

### Une valeur affichée décrit-elle encore la salle ?

Pas toujours, et l'application mobile doit le signaler. Le contrat MQTT précise qu'un objet en mode `pause` **reste connecté** et continue de répondre aux commandes : seule sa télémétrie s'arrête (voir [contrat-mqtt.md](contrat-mqtt.md#disponibilité-et-reconnexion)). `device.online` (disponibilité) et `latest_telemetry.bucket` (fraîcheur de la mesure) sont donc deux informations indépendantes qui peuvent diverger.

Côté mobile, [`isTelemetryStale`](../mobile/src/utils/telemetry.ts) compare `observed_at` à `STALE_TELEMETRY_MS` (30 s, soit ~6 fois la cadence normale du simulateur). Le composant [`DeviceCard`](../mobile/src/components/explore/device-card.tsx) affiche alors un badge distinct « ⏳ Mesure ancienne », indépendant du badge de connectivité « En ligne / Hors ligne ». Un objet peut donc apparaître **en ligne avec une mesure ancienne** : c'est la valeur affichée, pas l'objet, qui n'est plus fiable.

### Le téléphone est-il déconnecté, ou est-ce l'objet ?

Trois signaux distincts sont exposés séparément dans l'application, pour ne jamais confondre une coupure réseau du téléphone avec un objet indisponible ou une mesure simplement ancienne :

| Signal                   | Origine                                                                       | Où il est affiché                                        |
| ------------------------ | ----------------------------------------------------------------------------- | -------------------------------------------------------- |
| Réseau du téléphone      | `NetInfo` via [`useNetworkStatus`](../mobile/src/hooks/use-network-status.ts) | Bandeau « 📴 Hors ligne » global sur l'écran Capteurs    |
| Disponibilité de l'objet | `device.online` (topic `availability` / Last Will MQTT, backend)              | Badge « En ligne / Hors ligne » sur chaque carte capteur |
| Fraîcheur de la mesure   | `latest_telemetry.bucket` comparé à `STALE_TELEMETRY_MS`                 | Badge « ⏳ Mesure ancienne » sur chaque carte capteur    |

Si le bandeau global est affiché, c'est le téléphone (ou le réseau local) qui est coupé — l'app le sait via `NetInfo`, indépendamment de l'état de chaque capteur. Si seul un objet particulier passe « Hors ligne » alors que le reste de l'écran se met à jour normalement, c'est cet objet (perte de connexion MQTT / Last Will) qui est en cause, pas le téléphone.

### Comment reprendre sans doubler l'historique ni remplacer une mesure récente par une ancienne ?

Deux garde-fous, à deux niveaux :

- **Backend** : `Telemetry` utilise `message_id` comme clé primaire et l'insertion se fait via `insertOrIgnore` dans [`StoreTelemetryBatch`](../backend/app/Listeners/StoreTelemetryBatch.php) (déclenché par l'événement `TelemetryBatchReceived`) — un message rejoué (même `message_id`, cas `duplicate`) est ignoré silencieusement, sans doublon en base. La « dernière mesure » d'un objet est calculée via [`Device::latestTelemetry`](../backend/app/Models/Device.php) qui utilise `TelemetryOneMinute` (`telemetry_1m`, vue continue TimescaleDB à la minute) avec `ofMany(['bucket' => 'MAX'])` : c'est **le plus grand bucket** (minute la plus récente), pas la dernière ligne insérée. Un message en retard (cas `delay`, horodaté dans le passé) tombe dans un vieux bucket et ne peut jamais écraser la minute courante.
- **Mobile** : chaque requête RTK Query (`getDevices`, `getDeviceTelemetry`) **remplace intégralement** le résultat en cache au lieu de l'accumuler (pas de fusion/append côté client). À la reprise réseau, `refetchOnReconnect`/`refetchOnFocus` déclenchent un nouveau fetch complet qui remplace l'historique affiché — aucune mesure locale n'est donc rejouée ou doublée par l'app elle-même. Voir la décision [docs/decisions/0003-cache-mobile-hors-ligne.md](decisions/0003-cache-mobile-hors-ligne.md).

## Preuves reproductibles

Prérequis : kit démarré (`docker compose up -d --build --wait`) et application mobile lancée (`cd mobile && npx expo start`) sur le même réseau que l'API.

### 1. Doublon

```sh
docker compose run --rm tools incident sensor-001 duplicate
```

- Observer les logs `[api] ← /devices` (ajoutés dans [`store/api.ts`](../mobile/src/store/api.ts)) au prochain sondage : le point le plus récent ne change pas de valeur ni de date.
- Le graphique de la carte `sensor-001` ne montre pas de point dupliqué à la même date.

### 2. Mesure ancienne

```sh
docker compose run --rm tools incident sensor-001 pause
```

- Attendre plus de 30 secondes (`STALE_TELEMETRY_MS`).
- Sur la carte `sensor-001` : le badge de connectivité reste « En ligne », mais le badge « ⏳ Mesure ancienne » apparaît sous l'horodatage — preuve que les deux signaux sont bien dissociés.

```sh
docker compose run --rm tools incident sensor-001 resume
```

- Le badge « ⏳ Mesure ancienne » disparaît dès la mesure suivante.

### 3. Coupure réseau

Deux façons de reproduire, au choix :

- **Côté téléphone** : activer le mode avion pendant que l'écran Capteurs est ouvert.
- **Côté serveur** (sans toucher au téléphone) : `docker compose stop nginx` (ou couper le Wi-Fi de l'ordinateur qui héberge l'API).

Résultat attendu : le bandeau « 📴 Hors ligne » apparaît, les dernières données connues restent affichées, et le texte « Dernière mise à jour : HH:mm:ss » se fige à l'heure du dernier succès. Les logs Metro continuent de montrer des tentatives (`[api] → ...` suivi d'échecs) toutes les 5 secondes.

### 4. Reprise

```sh
docker compose start nginx
```

(ou désactiver le mode avion / reconnecter le Wi-Fi)

Résultat attendu :

- Un nouvel appel `[api] → /devices` part immédiatement (pas d'attente du prochain sondage à 5 s), déclenché par `refetchOnReconnect` ([`store/index.ts`](../mobile/src/store/index.ts)).
- Le bandeau « 📴 Hors ligne » disparaît et « Dernière mise à jour » se met à jour.
- L'historique du graphique reste chronologiquement cohérent (pas de point dupliqué ni de retour en arrière), conformément aux garde-fous du point 3 ci-dessus.
