# J4 — Commander un objet et confirmer l'exécution

## 1. Quelle différence entre une commande acceptée, publiée, reçue et exécutée ?

Le cycle de vie d'une commande traverse quatre états distincts que le backend trace explicitement.

**Acceptée → `PENDING`**
La commande est persistée en base (`commands:create`) avec un `command_id` UUID, une `issued_at` et une `timeout_at` calculée à `issued_at + 30 s`. À ce stade le backend garantit uniquement que la demande est enregistrée ; aucun message n'a encore quitté le backend.

Voir [`SendCommand.php`](../backend/app/Actions/SendCommand.php) lignes 25-33.

**Publiée → `SENT`**
Le backend publie le payload sur `campus/v1/devices/{device_id}/commands` via MQTT. Si la publication réussit (le broker accepte le message), le statut passe à `SENT` et `sent_at` est horodaté.
Si la publication échoue (broker injoignable, exception réseau), le statut passe directement à `FAILED`.

Ce que `SENT` garantit : le broker a accepté le message. Ce qu'il **ne garantit pas** : que l'objet l'a reçu. En QoS 1, le broker livrera le message dès que l'objet se reconnecte, mais le backend n'en saura rien.

**Reçue par l'objet** — *aucun statut dédié*
Il n'existe pas de statut « reçu » entre `SENT` et `ACKNOWLEDGED`. C'est le gap fondamental d'un système distribué asynchrone : le backend publie dans le vide et attend. Si l'objet est hors ligne, la commande reste `SENT` jusqu'à ce que `timeout_at` soit dépassé.

**Exécutée → `ACKNOWLEDGED` ou `FAILED`**
L'objet publie un résultat sur `campus/v1/devices/{device_id}/results` avec le même `command_id`. Le subscriber reçoit le message, `HandleCommandResult` cherche la commande en base par `command_id` et met à jour le statut :
- `status: executed` dans le résultat → `ACKNOWLEDGED`, `acked_at` horodaté
- `status: rejected` → `FAILED`

**Timeout → `TIMEOUT`**
Le statut `TIMEOUT` n'est pas écrit en base par le flux normal. Il est calculé à la lecture par l'accesseur `getEffectiveStatusAttribute()` : si le statut n'est pas terminal et que `timeout_at` est dépassé, l'API retourne `TIMEOUT`. Cela signifie qu'une commande `SENT` dont l'objet n'a jamais répondu apparaît comme `TIMEOUT` côté client sans qu'aucune écriture supplémentaire ne soit nécessaire.

## 2. Comment rattacher la réponse de l'objet à la bonne commande ?

La corrélation repose sur le `command_id` inclus dans les deux sens du flux.

**Côté backend**, `SendCommand::buildPayload()` intègre le `command_id` dans le payload MQTT :

```json
{
  "schema_version": 1,
  "command_id": "018f4b2e-7c3a-7000-9e1d-abcdef123456",
  "action": "set_ventilation",
  "enabled": true,
  "expires_at": "2026-10-07T14:32:30.000Z"
}
```

**Côté simulateur**, `Device.execute()` (`model.py`) valide le `command_id`, exécute l'action et l'echo dans le résultat :

```json
{
  "schema_version": 1,
  "device_id": "sensor-01",
  "command_id": "018f4b2e-7c3a-7000-9e1d-abcdef123456",
  "status": "executed",
  "executed_at": "2026-10-07T14:32:28.000Z",
  "ventilation": true
}
```

**Côté backend**, `HandleCommandResult` fait `Command::find($r->command_id)`. C'est une recherche par clé primaire UUID — O(1), sans ambiguïté possible entre devices.

## 3. Que fait le système si l'objet est hors ligne, si l'ACK est perdu ou arrive après le timeout ?

### Objet hors ligne

Le broker MQTT (QoS 1) stocke le message pour l'objet s'il est connecté en session persistante. Si l'objet est complètement hors ligne et ne se reconnecte pas avant `timeout_at`, la commande reste `SENT` et l'accesseur `effective_status` retourne `TIMEOUT` à la lecture. Aucune nouvelle tentative automatique n'est émise.

Pour produire ce scénario de façon reproductible, on envoie `no-response` au simulateur via le topic de contrôle :

```bash
mosquitto_pub -h localhost -u teacher -P teacher-demo \
  -t 'campus/v1/simulator/{device_id}/control' \
  -m '{"action":"no-response","request_id":"test-1"}'
```

Le simulateur reçoit les commandes mais n'émet aucun résultat. Après 30 secondes, `GET /api/devices/{id}/commands` retourne `"status": "TIMEOUT"`.

**Log de traçage** (filter `commandId`) :
```
command.issued  → status: PENDING
command.sent    → status: SENT
(silence)
```

### ACK perdu

En QoS 1, le broker peut livrer le message deux fois au subscriber si l'ACK MQTT est perdu. `HandleCommandResult` protège contre ce cas avec une vérification `CommandResult::where('command_id')->exists()` avant l'écriture : le second ACK est détecté et loggué `command.duplicate` sans provoquer de double exécution.

### ACK tardif (après `timeout_at`)

Un ACK peut arriver alors que `timeout_at` est dépassé mais que le statut en base est encore `SENT` (le job d'expiration ne s'est pas encore exécuté). Dans ce cas, `$command->status->isTerminal()` retourne `false` et le code actuel accepte et écrit l'ACK comme `ACKNOWLEDGED`.

Le comportement documenté pour ce cas est défini dans [`docs/decisions/0004-command-lifecycle.md`](decisions/0004-command-lifecycle.md).

## 4. Que se passe-t-il si la même commande est reçue deux fois ?

**Côté simulateur** (`model.py`, `Device.execute()`) : idempotence native. Le simulateur conserve un dictionnaire `results` indexé par `command_id`. Si la même commande arrive une deuxième fois avec le même contenu, le résultat précédent est retourné sans ré-exécuter l'action. Si le contenu diffère (même `command_id`, payload différent), `ValueError` est levée et un résultat `rejected` est publié.

**Côté backend** (`HandleCommandResult`) : `CommandResult::where('command_id', $r->command_id)->exists()` détecte le doublon avant tout `create`. Le second ACK est ignoré et loggué `command.duplicate`. Le statut de la commande reste inchangé.

Ce comportement rend l'opération **idempotente de bout en bout** : rejouer un résultat ne change pas l'état final du système.

Pour produire ce scénario, on envoie `duplicate` au simulateur :

```bash
mosquitto_pub -h localhost -u teacher -P teacher-demo \
  -t 'campus/v1/simulator/{device_id}/control' \
  -m '{"action":"duplicate","request_id":"test-2"}'
```

**Log attendu** (filter `commandId`) :
```
command_result.received  → status: executed   (premier ACK, traité)
command.duplicate        → (second ACK, ignoré)
command.acknowledged
```

## Preuves des jalons

### Flux complet mobile → backend → MQTT → objet → ACK → backend → mobile

1. Mobile : `POST /api/devices/{id}/commands` avec `{"action":"set_ventilation","params":{"enabled":true}}`
2. Backend log : `command.issued` (PENDING) → `command.sent` (SENT)
3. Simulateur reçoit et publie sur `results`
4. Backend log : `command_result.received` → `command.acknowledged` (ACKNOWLEDGED)
5. SSE event `{"type":"state","device_id":"...","ventilation":true}` envoyé au mobile
6. Mobile : état mis à jour en temps réel sans refresh

Filtrer les logs par `commandId` pour reconstruire le parcours complet.

### Timeout reproductible

```bash
# 1. Activer le mode no-response
mosquitto_pub -h localhost -u teacher -P teacher-demo \
  -t 'campus/v1/simulator/{device_id}/control' \
  -m '{"action":"no-response","request_id":"r1"}'

# 2. Envoyer une commande depuis le mobile

# 3. Attendre 30 secondes

# 4. Vérifier
curl http://localhost:8000/api/devices/{id}/commands
# → "status": "TIMEOUT"

# 5. Remettre en mode normal
mosquitto_pub -h localhost -u teacher -P teacher-demo \
  -t 'campus/v1/simulator/{device_id}/control' \
  -m '{"action":"respond","request_id":"r2"}'
```

### ACK tardif ou perdu

Utiliser `delay` pour forcer un telemetry retardé (preuve de mécanisme de timestamp) ou activer `no-response` puis `respond` après expiration du timeout.

### Commande dupliquée

```bash
mosquitto_pub -h localhost -u teacher -P teacher-demo \
  -t 'campus/v1/simulator/{device_id}/control' \
  -m '{"action":"duplicate","request_id":"r3"}'
```

Le simulateur publie deux fois le même résultat. Le backend loggue `command.duplicate` sur le second.
