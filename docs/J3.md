# Question

# Gestion des capteurs et fiabilité des données

## 1. Comment distinguer sans ambiguïté plusieurs capteurs simulés qui publient en parallèle ?

Chaque capteur possède un **identifiant unique** (`device_id`) qui est utilisé dans les messages MQTT.

Par exemple :

```text
sensor-001
sensor-002
sensor-003
```

L'identifiant est intégré au topic MQTT :

```text
sensors/{device_id}/telemetry
```

Exemples :

```text
sensors/sensor-001/telemetry
sensors/sensor-002/telemetry
sensors/sensor-003/telemetry
```

Ainsi, même si plusieurs capteurs publient simultanément, le backend peut toujours déterminer l'origine de chaque mesure.

Le payload contient également l'identifiant du capteur afin de permettre une vérification de cohérence :

```json
{
  "device_id": "sensor-001",
  "observed_at": "2026-09-17T09:20:00Z",
  "temperature": 22.4,
  "co2": 650
}
```

Le `device_id` doit être unique et associé à une seule salle dans le système.

---

## 2. Quelles données entrantes doivent être refusées avant d’atteindre le cœur du système ?

Les données doivent être validées dès leur réception, avant leur traitement métier et leur stockage.

Les messages suivants doivent être refusés :

- message MQTT provenant d'un topic inconnu ;
- `device_id` absent ou inconnu ;
- payload qui n'est pas un JSON valide ;
- champs obligatoires absents ;
- types incorrects, par exemple une température sous forme de texte ;
- valeurs hors limites physiques acceptables ;
- date `observed_at` absente ou invalide ;
- identifiant de capteur incohérent avec le topic MQTT ;
- message trop ancien si sa fenêtre d'acceptation est dépassée ;
- message dépassant une taille maximale définie ;
- données contenant des champs inattendus ou non autorisés selon le schéma défini.

Exemple de validation :

```json
{
  "device_id": "sensor-001",
  "observed_at": "2026-09-17T09:20:00Z",
  "temperature": 22.4,
  "co2": 650
}
```

Si la température vaut par exemple `"abc"` ou que le `device_id` n'existe pas, le message est rejeté.

Cette validation permet d'éviter que des données invalides atteignent Laravel et TimescaleDB.

## 3. Comment détecter qu’un capteur ne fournit plus une information suffisamment fraîche ?

Le système utilise la date `last_seen_at` du capteur.

À chaque message valide reçu, cette date est mise à jour.

On définit ensuite un seuil de fraîcheur, par exemple :

```text
fresh = dernière donnée reçue il y a moins de 60 secondes
stale = dernière donnée reçue il y a plus de 60 secondes
offline = aucune donnée reçue depuis un délai plus important
```

Exemple :

```text
sensor-001
last_seen_at = 09:20:00
heure actuelle = 09:20:30

=> données fraîches
```

Si :

```text
heure actuelle = 09:22:00
```

alors la donnée est considérée comme trop ancienne.

Le backend peut exposer cet état dans l'API :

```json
{
  "id": "sensor-001",
  "online": false,
  "last_seen_at": "2026-09-17T09:20:00Z"
}
```

La valeur de `online` ne doit donc pas uniquement dépendre de la connexion MQTT : elle doit également tenir compte de la fraîcheur des dernières données reçues.

## 4. Comment le système se comporte-t-il lorsqu’un message est dupliqué, retardé ou invalide ?

### Message dupliqué

Chaque mesure possède un identifiant unique ou une combinaison permettant de l'identifier, par exemple :

```text
device_id + observed_at
```

Un même message reçu plusieurs fois ne doit pas créer plusieurs mesures identiques dans TimescaleDB.

Le backend vérifie donc si la mesure existe déjà avant de l'enregistrer.

Cela permet de rendre le traitement **idempotent**.

---

### Message retardé

Un message peut arriver après des mesures plus récentes.

La date `observed_at` permet de remettre la mesure dans le bon ordre chronologique.

Une donnée retardée peut être acceptée si elle reste dans une fenêtre temporelle acceptable.

Par exemple :

```text
donnée reçue : 09:20
dernière donnée : 09:25
```

La donnée de 09:20 peut être stockée comme donnée historique, mais elle ne doit pas remplacer la dernière valeur connue de 09:25.

---

### Message invalide

Un message invalide est rejeté avant son insertion dans la base de données.

Le système peut journaliser le rejet avec :

- le capteur concerné ;
- la raison du rejet ;
- la date de réception ;
- le topic MQTT concerné.

Une erreur sur un message ne doit pas bloquer le traitement des messages provenant des autres capteurs.

---

## 5. Que se passe-t-il si le broker MQTT devient indisponible puis revient ?

Lorsque Mosquitto devient indisponible, les capteurs simulés tentent automatiquement de se reconnecter.

Pendant l'indisponibilité :

```text
Capteur
   |
   X
Mosquitto
```

Aucune nouvelle donnée ne peut atteindre le backend.

Le backend ne doit cependant pas considérer immédiatement tous les capteurs comme définitivement hors service. Leur état dépend de la dernière donnée reçue et du délai de fraîcheur défini.

Lorsque Mosquitto revient :

```text
Capteur
   |
   v
Mosquitto
   |
   v
Laravel
```

Les capteurs se reconnectent et reprennent leurs publications.

Pour éviter les pertes ou doublons, la reconnexion doit utiliser :

- un mécanisme de reconnexion automatique ;
- un `client_id` MQTT unique par capteur ;
- un niveau de QoS adapté ;
- si nécessaire, des messages persistants ou une file d'attente côté producteur.

Le backend continue normalement à traiter les nouveaux messages après le retour du broker.

## 6. Quels secrets et paramètres de configuration ne doivent jamais être versionnés dans Git ?

Les informations sensibles ne doivent jamais être présentes directement dans le dépôt Git.

Cela concerne notamment :

- mots de passe PostgreSQL ;
- identifiants MQTT ;
- mots de passe MQTT ;
- clés API ;
- tokens d'authentification ;
- secrets Laravel (`APP_KEY`) ;
- certificats et clés privées ;
- secrets JWT ;
- identifiants de services externes ;
- variables contenant des données personnelles ou sensibles.

Ces informations doivent être fournies par l'environnement d'exécution, par exemple avec un fichier `.env` local qui est ignoré par Git :

```gitignore
.env
.env.*
!.env.example
```

Un fichier `.env.example` peut être versionné afin de documenter les paramètres nécessaires :

```env
APP_KEY=

DB_HOST=
DB_DATABASE=
DB_USERNAME=
DB_PASSWORD=

MQTT_HOST=
MQTT_PORT=
MQTT_USERNAME=
MQTT_PASSWORD=
```

Les valeurs réelles ne doivent jamais être écrites dans ce fichier.

En production, les secrets doivent être injectés via les variables d'environnement ou un gestionnaire de secrets adapté.

## Synthèse

Le système repose donc sur plusieurs mécanismes complémentaires :

| Problème                       | Mécanisme                                           |
| ------------------------------ | --------------------------------------------------- |
| Identifier les capteurs        | `device_id` unique                                  |
| Identifier l'origine MQTT      | Topic contenant le `device_id`                      |
| Empêcher les données invalides | Validation du payload                               |
| Détecter les données anciennes | `last_seen_at` + seuil de fraîcheur                 |
| Éviter les doublons            | Traitement idempotent                               |
| Gérer les messages retardés    | `observed_at`                                       |
| Gérer les messages invalides   | Rejet + journalisation                              |
| Gérer une coupure MQTT         | Reconnexion automatique                             |
| Protéger les secrets           | Variables d'environnement / gestionnaire de secrets |
